# Регламент миграций базы данных (migrations/GEMINI.md)

Данные правила применяются при создании, проверке и применении миграций базы данных через Alembic в директории `migrations/`.

---

## 1. Жизненный цикл миграций

Каждое изменение ORM-моделей в `app/models/` должно сопровождаться отдельной версионированной миграцией Alembic.

### Шаг 1. Генерация файла миграции
Использовать осмысленное имя ревизии:
```bash
alembic revision --autogenerate -m "add_category_field_to_transactions"
```

### Шаг 2. Обязательная ручная проверка файла ревизии
Автогенерация Alembic не всегда идеальна. Перед сохранением проверить сгенерированный файл в `migrations/versions/`:
* Убедиться, что `upgrade()` содержит только намеренные изменения.
* **Обязательно проверить `downgrade()`**: откат миграции должен полностью возвращать схему в исходное состояние без ошибок.
* Проверить генерацию ENUM-типов и внешних ключей (`ondelete`).

---

## 2. Безопасность миграций в Production

* **Добавление обязательных (NOT NULL) колонок**:
  * Нельзя добавлять `nullable=False` без дефолтного значения (`server_default`) в существующие заполненные таблицы.
* **Удаление колонок или таблиц**:
  * Избегать разрушительных удалений без предварительного вывода из кода приложения (zero-downtime подход).
* **Создание индексов**:
  * Для больших таблиц в production помнить про блокировки (в PostgreSQL использовать `CONCURRENTLY` при необходимости).

---

## 3. Команды для пользователя

После генерации или обновления миграций агент обязан уведомить пользователя и предоставить команду для применения:

```bash
# Применить миграции до актуального состояния
alembic upgrade head

# Откатить последнюю миграцию (при необходимости)
alembic downgrade -1

# Посмотреть текущую примененную версию
alembic current
```
