# Чек-лист проверок приложения

В этом документе описаны проверки, которые выполняются автоматическими тестами (Unit и Интеграционные), а также сценарии для ручного тестирования, которые сложно или нецелесообразно покрывать автотестами.

## Автоматизированные тесты (pytest)

### 1. Авторизация и Управление пользователями (Auth Service)
*   [x] **Регистрация:**
    *   Успешное создание нового пользователя (сохранение хэша пароля, email, имени).
    *   Попытка регистрации с уже существующим email (ожидается `BadRequestException`).
*   [x] **Аутентификация (Login):**
    *   Успешный вход с правильными email и паролем (возвращаются access и refresh токены).
    *   Попытка входа с неверным паролем (ожидается 401).
    *   Попытка входа несуществующего пользователя (ожидается 401).
*   [x] **Управление токенами:**
    *   Успешная ротация токенов с использованием валидного refresh токена (старый токен становится `revoked`).
    *   Отказ в обновлении токена, если использован отозванный (`revoked`) refresh токен (ожидается 401).
    *   Отказ в обновлении токена, если использован истекший refresh токен (ожидается 401).
    *   Отказ, если вместо refresh токена передан access токен.
*   [x] **Выход из системы (Logout):**
    *   Успешный выход с пометкой текущего access токена как `revoked`.
    *   Попытка использования `revoked` токена для доступа к защищенным эндпоинтам (например, `/me` возвращает 401).
    *   Попытка деактивации несуществующего токена.
*   [x] **OAuth Авторизация:**
    *   Успешный вход или регистрация через Google (проверка валидации id_token и создания пользователя).
    *   Успешный вход или регистрация через Apple (проверка валидации identity_token и создания пользователя).
    *   Сохранение URL аватара при входе через Google.
*   [x] **Профиль пользователя и базовая валюта (`PATCH /api/v1/auth/me`):**
    *   Успешное получение базовой валюты по умолчанию (`RUB`) в `GET /auth/me`.
    *   Успешное обновление имени, URL аватара и базовой валюты (`base_currency` -> `UZS`, `USD`, `EUR`, `KZT`).
    *   Валидация допустимых кодов валют через централизованный перечень `CurrencyCode` (отклонение неподдерживаемой валюты со статусом 422).
    *   Защита эндпоинта от неавторизованного доступа (401 / 403).
    *   Автоматический подхват базовой валюты пользователя в AI-инсайтах (`/api/v1/insights/`), если параметр `currency` не передан клиентом.
    *   Автоматический пересчет финансов: атомарный пересчет `exchange_rate` и `base_amount` всех транзакций пользователя, конвертация лимитов бюджетов (`limit_amount`) и инвалидация кэша AI-инсайтов при смене `base_currency`.

### 2. Транзакции (Transaction Service)
*   [x] **Создание:** Успешное добавление транзакции (доход или расход).
*   [x] **Чтение:** Получение списка транзакций пользователя с фильтрацией (по датам, категориям и типу).
*   [x] **Обновление:** Изменение суммы, категории или даты существующей транзакции.
*   [x] **Удаление:** Удаление транзакции.
*   [x] **Изоляция данных:** Пользователь не может получить, изменить или удалить транзакцию другого пользователя.
*   [x] **Валидация:** Проверка на отрицательные суммы или некорректные типы операций.
*   [x] **Категории доходов:** Поддержка расширенных категорий (`freelance`, `investments`, `transfers`, `cashback`, `sales`). Валидация несовместимых категорий (отклонение `food` для дохода, отклонение `salary` для расхода с кодом 422).
*   [x] **Глобальный ETag и курсорная пагинация (`GET /transactions`):** ETag вычисляется по всей коллекции пользователя без привязки к `limit`/`cursor`. Заголовок `ETag` отдается только на первой странице выборки; страницы пагинации (`cursor != null`) не возвращают 304 и ETag. Запрос первой страницы с валидным `If-None-Match` возвращает 304 с заголовком `ETag`.

### 3. Бюджеты (Budget Service)
*   [x] **Создание:** Установка лимита бюджета на определенную категорию и месяц/год.
*   [x] **Валидация категорий бюджета:** Бюджеты разрешены только для категорий расходов (`EXPENSE_CATEGORIES`); попытка установить бюджет на доходы отклоняется с кодом 422.
*   [x] **Мультивалютный подсчет spent и remaining:** Конвертация транзакций в разных валютах в `user.base_currency` по курсу транзакции или актуальному суточному курсу.
*   [x] **Пересчет лимитов и инвалидация ETag:** Автоматический пересчет `limit_amount` всех бюджетов пользователя при смене `base_currency` в `PATCH /api/v1/auth/me` и инвалидация заголовка `ETag` (клиент с сохраненным ETag получает 200 OK вместо 304).
*   [x] **Проверка лимитов:** Расчет процента использования бюджета (превышение лимитов) на основе транзакций в этой категории.
*   [x] **Управление:** Обновление и удаление бюджетов, изоляция бюджетов между пользователями.

### 4. Синхронизация и Интеграции (Sync Service)
*   [x] Проверка логики обмена и синхронизации данных (состояние до и после синхронизации).
*   [x] **Идемпотентный UPSERT бюджетов:** Корректное сохранение и обновление бюджетов по ID или составному ключу `(category, month, year)` без дубликатов и без падения по уникальным констрейнтам.
*   [x] **Дедупликация пакетов:** Обработка повторяющихся элементов в пакете синхронизации и исключение дубликатов в ответе `synced_budgets`.
*   [x] **Лимит объема пакета:** Пакеты, содержащие более 500 элементов в списках транзакций, бюджетов или удалений, валидируются и отклоняются со статусом 422 (`max_length=500`).
*   [x] **Изоляция конфликтующих/чужих ID (TASK-12):** При передаче ID транзакции или бюджета, уже занятого другим пользователем, запись безопасно отклоняется в поле `rejected`, предотвращая падение всего батча со статусом 500.
*   [x] **Объединенное удаление (N+1 оптимизация):** Удаление бюджетов из всех источников пакета (`deleted_budget_ids`, `deleted_budgets`, `check_deleted`) выполняется единым агрегированным SQL-запросом.
*   [x] **Устранение N+1 при коммите:** Сохранение объектов с `expire_on_commit=False` исключает отдельный цикл `refresh()` по каждой записи.
*   [x] **Корректная обработка исключений (TASK-13):** Непредвиденные системные сбои возвращают 500 `SYNC_FAILED` (вместо маскировки под 400), а доменные `AppException` пробрасываются с исходными кодами и деталями.
*   [x] **Пакетное удаление транзакций (`deleted_transaction_ids`):** Идемпотентное удаление списка транзакций пользователя единым SQL-запросом; чужие транзакции защищены от удаления, повторные запросы успешны.
*   [x] Целостность: Данные не теряются и не дублируются при многократной синхронизации.

### 5. ИИ и Инсайты (AI Service)
*   [x] Генерация текстовых или аналитических сводок по финансам на основе истории транзакций.
*   [x] Отработка ошибок при недоступности внешнего API (если мокается).
*   [x] Проверка кэширования или лимитирования запросов к ИИ.
*   [x] Отказоустойчивость Redis: при сетевом сбое или недоступности кэша сервис не падает с ошибкой 500, а прозрачно выполняет запрос к модели, возвращает ответ и логирует предупреждение.
*   [x] **Неблокирующая инвалидация кэша (TASK-05):** Инвалидация и очистка кэша инсайтов выполняются через `scan_iter` и `unlink` пачками по 500 ключей без блокирующего `KEYS` и без деструктивного `FLUSHDB`.
*   [x] **Инвалидация кэша инсайтов при смене валюты (TASK-04):** Смена базовой валюты в `PATCH /api/v1/auth/me` вызывает `AIService.invalidate_cache(user_id)` и корректно очищает ключи кэша рекомендаций пользователя в Redis.

### 6. Безопасность и Валидация (Security & Errors)
*   [x] Rate Limiting: Блокировка при превышении числа запросов (включая лимит 10/мин на `PATCH /api/v1/auth/me`).
*   [x] Обработка общих ошибок: Возврат стандартизированных JSON-ответов для 400, 401, 403, 404, 500 ошибок (соответствие `RESPONSE_FORMAT.md`).
*   [x] Unit of Work: Транзакции БД откатываются (rollback) при возникновении ошибки в бизнес-логике.

### 7. Мультивалютность и Котировки (Multi-Currency & Rates)
*   [x] **Создание транзакции:** Поддержка валюты операции (`currency`), курса (`exchange_rate`) и расчет базовой суммы (`base_amount`).
*   [x] **Финансовая точность:** Квантование `base_amount` до 2 знаков после запятой (`ROUND_HALF_UP`) с исключением погрешностей IEEE-754.
*   [x] **Валидация:** Отклонение отрицательного `base_amount` (422), некорректной длины кода валюты (422) и отрицательного курса (422).
*   [x] **Пересчет бюджетов:** Агрегация фактических расходов (`spent`) и остатка лимита (`remaining`) строго по `base_amount`.
*   [x] **Мультивалютный пересчет лимитов:** Автоматический пересчет лимитов всех бюджетов по кросс-курсу при смене `user.base_currency` через `PATCH /api/v1/auth/me` с инвалидацией ETag.
*   [x] **Защита от переполнения NUMERIC:** Поддержка сумм свыше $10^{10}$ в валютах с крупным номиналом (UZS и др.) благодаря стандарту `NUMERIC(18, 2)` для сумм и `NUMERIC(18, 6)` для курсов без ошибок `NumericValueOutOfRangeError`.
*   [x] **Строгая валидация кодов валют:** Проверка по справочнику `SUPPORTED_CURRENCIES` в `TransactionCreate` и `TransactionSyncItem`; отклонение неподдерживаемых кодов (`ABC`, `usdt` и др.) со статусом 422 в `POST /transactions` и `POST /sync`.
*   [x] **Защита целостности в БД (CHECK Constraints):** Ограничения `ck_users_base_currency` и `ck_transactions_currency` на уровне схемы PostgreSQL.
*   [x] **Подстановка базовой валюты пользователя по умолчанию:** Транзакции без указания `currency` автоматически получают `user.base_currency`, курс 1.0 и `base_amount = amount` как в `POST /transactions`, так и в `POST /sync`.
*   [x] **Единое согласование сумм и курсов (`CurrencyService.resolve_amounts`):** Единый расчет для create и sync; при совпадении валюты всегда `rate=1.0` и `base_amount=amount` с защитой от искажения данных; валидация клиентского курса против серверного кросс-курса с допуском `CLIENT_RATE_TOLERANCE_PERCENT` (по умолчанию 15%); расчет `base_amount` сервером по формуле `amount * rate`.
*   [x] **Предметные ошибки котировок:** Вызов `CurrencyService.calculate_cross_rate` для неизвестной валюты выбрасывает `InvalidCurrencyException`.
*   [x] **Атомарный Upsert бюджетов (защита от race conditions):** Повторный вызов `POST /budgets/` с тем же периодом и категорией обновляет лимит без 500 ошибки уникального ключа.
*   [x] **Спецификация ETag/304 для бюджетов:** 304 Not Modified возвращает заголовок `ETag`, поддерживает слабый валидатор `W/` и списки тегов в `If-None-Match`.
*   [x] **Инвалидация ETag бюджетов:** ETag бюджетов инвалидируется при создании/удалении транзакций, бюджетов, синхронизации и смене базовой валюты.
*   [x] **Производительность бюджетов и ленивая загрузка котировок:** Чтение `GET /budgets` агрегирует расходы напрямую в SQL без вызова `CurrencyService.get_rates()`; `POST /sync` запрашивает котировки только при наличии мультивалютных транзакций.
*   [x] **Негативный кэш при сбое шлюза (TASK-09):** При сетевом сбое внешнего шлюза сервис записывает fallback-котировки в негативный кэш Redis с коротким TTL (180 с) и флагом `is_fallback=True`, исключая подвисания и таймауты повторных запросов.
*   [x] **Постоянный источник fallback-котировок:** Резервные котировки считываются из постоянного ключа `currency_rates:last_successful:USD` вместо устаревших статических констант.
*   [x] **Переиспользование HTTP-клиента:** Использование общего пула соединений через синглтон `httpx.AsyncClient` с корректным освобождением в `lifespan`.
*   [x] **Пакетный пересчет валют в SQL (TASK-06):** Смена базовой валюты пользователя пересчитывает курсы и базовые суммы транзакций и лимиты бюджетов одним SQL UPDATE с CASE-выражением без загрузки объектов в память; транзакции в новой валюте получают rate=1.0, а цикл смены валюты (RUB->USD->RUB) полностью обратим без дрейфа сумм.
*   [x] **Параллельные запросы бюджетов без 500 ошибки (TASK-14):** Одновременные асинхронные вызовы `POST /budgets/` на одну категорию и период успешно отрабатывают с HTTP 201 (Upsert) без IntegrityError и 500 ошибки гонки (`test_create_budget_parallel_requests_no_500`).
*   [x] **Централизованный клиент и билдеры ключей Redis (TASK-16):** Единый модуль `app/redis.py` с пулом соединений, закрытием в `lifespan`, типобезопасными генераторами ключей и устранением перекрестных импортов между сервисами (`test_redis_module.py`).
*   [x] **Метаданные и честная дата fallback-котировок (TASK-17):** Резервные котировки из таблицы содержат фиксированную дату ее актуализации (`FALLBACK_RATES_UPDATED_AT`), исключая ложную свежесть устаревших данных, и помечаются флагом `is_fallback=True`.
*   [x] **HTTP-кэширование и санитизация котировок:** `GET /currencies/rates` возвращает `Cache-Control: public, max-age=3600`, а парсер внешнего шлюза отсекает неположительные и некорректные значения курсов.

## Ручное тестирование (Manual QA)

Эти проверки сложно полностью автоматизировать или они требуют проверки UI/внешних систем.

*   [ ] **Интеграция с реальными LLM (AI Service):** Проверить адекватность реальных советов от ИИ на нестандартных наборах транзакций без моков. Убедиться, что время ответа приемлемо.
*   [ ] **Проверка Rate Limiter в боевых условиях:** Провести нагрузочное тестирование с реальных IP адресов или через балансировщик, чтобы убедиться, что `X-Forwarded-For` или реальные IP корректно определяются.
*   [ ] **Concurrent requests (Состояние гонки):** При быстром клике "создать транзакцию" в UI убедиться, что транзакция не дублируется.
*   [ ] **Синхронизация на плохой сети:** Имитация потери пакетов (throttle network в DevTools браузера/телефона) при вызове `/sync` или долгих запросах, чтобы убедиться, что приложение не зависает и корректно показывает ошибку таймаута.
*   [ ] **UI/UX: Истечение сессии:** Оставить вкладку открытой до истечения срока действия refresh токена. Убедиться, что при возобновлении активности приложение плавно переводит пользователя на экран логина без показа "сырых" 401 ошибок.
*   [ ] **Одобрение и реальный вход через OAuth:** Протестировать вход с реальными Google и Apple аккаунтами из мобильного приложения. Убедиться, что внешние токены успешно обрабатываются сервером.
