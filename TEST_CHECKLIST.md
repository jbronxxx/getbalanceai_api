# Чек-лист проверок приложения

В этом документе описаны проверки, которые выполняются автоматическими тестами (Unit и Интеграционные), а также сценарии для ручного тестирования, которые сложно или нецелесообразно покрывать автотестами.

## Автоматизированные тесты (pytest)

### 1. Авторизация и Управление пользователями (Auth Service)
*   [x] **Email без учёта регистра:** при OAuth-входе email нормализуется (`strip().lower()`); вход с адресом в другом регистре попадает в существующий аккаунт (`TestOAuthEmailCaseInsensitive`).
*   [x] **Каскадное удаление аккаунта:** транзакции, бюджеты и токены удаляются БД (`ON DELETE CASCADE`), ORM их не загружает; в тестах SQLite включён `PRAGMA foreign_keys` (`TestAccountDeletionCascade`).
*   [x] **Уточнения контракта:** битый курсор — 400 `INVALID_CURSOR`; в `details.fields` путь к полю с индексом записи пакета; `POST /budgets` без валюты сохраняет валюту лимита; `Cache-Control` резервных курсов — короткий срок (`tests/test_api_contract_polish.py`).
*   [x] **Часовой пояс клиента:** разбор `X-Timezone-Offset` (вне диапазона и мусор → UTC); границы месяца и переход через год; ночная трата 1-го числа по UTC+5 входит в бюджет нового месяца, без заголовка — по UTC; ETag зависит от пояса; `/sync` и отпечаток AI-отчёта считают в поясе клиента (`tests/test_client_timezone.py`).
*   [x] **Сбой Redis:** авторизованный запрос — 503 `SERVICE_UNAVAILABLE`, `/health` — 503 с `redis: unhealthy` (`TestRedisOutage`).
*   [x] **Квота и таймаут AI:** из 10 параллельных запросов LLM вызывается 5 раз; ошибка LLM возвращает квоту; зависший вызов обрывается по таймауту; без Redis LLM не вызывается; транзакция БД завершается до вызова LLM; невалидные `currency`/`locale` — 422 (`TestInsightsQuotaAndTimeout`, `TestInsightsEndpointValidation`).
*   [x] **Голосовой ввод (`test_voice.py`):** несколько трат — несколько черновиков с суммами до копеек, ничего не сохраняется; без суммы — пустой список; инструкция на языке интерфейса (de → en без кириллицы), «сегодня» по `X-Timezone-Offset`, фраза одной строкой без управляющих символов и «|»; ответ модели исправляется или отбрасывается (тип, сумма, категория не к типу → `other`, чужая валюта, будущая дата, длина описания, не больше 10 записей); квота 30/сутки → 429 `AI_QUOTA_EXCEEDED`; ошибка, таймаут или неразборчивый ответ модели — 503, квота возвращается; без ключей LLM и без Redis модель не вызывается; фраза и ответ модели не попадают в журналы; без токена — 403; 422 на пустой/длинный текст, другую валюту и локаль.
*   [x] **Вызов LLM (`test_llm.py`):** запрос к Claude — `effort` из `AI_EFFORT`, адаптивные размышления, без `temperature`, таймаут попытки через `with_options`; ответ — только текстовые блоки (блок размышлений пропускается); запрос к Gemini — JSON-ответ, таймаут HTTP-запроса (мс), `temperature` из запроса; 529 дважды — третья попытка на Gemini (в журнале причина и код, без текста запроса); 500, 429, таймаут и обрыв соединения Claude повторяются; 401, 403, 402, лимит расходов, 400 и `max_tokens` — сразу Gemini без повтора; отказ (`refusal`) — сразу Gemini, расход отказа учтён, в журнале категория; все попытки неудачны — ошибка последней и `ai_requests_failed_total`; ошибка запроса на запасной — исключение; без запасной модели (или та же) — три попытки основной, постоянная ошибка без повтора; зависшая попытка обрывается и повторяется; после общего срока `AI_REQUEST_TIMEOUT` новых попыток нет; модели без ключа пропускаются (`sk-...` у Anthropic — шаблон), ключей нет — `ai_configured()` ложно и `generate` — исключение; причины сбоев Gemini и транспорта (503, 500, 429, 403, 400, таймауты, обрыв, приостановленная организация Anthropic).
*   [x] **Лимит `/sync`:** 61-й запрос в минуту от пользователя — 429 (`TestSyncRateLimit`).
*   [x] **Вход по паролю выведен из API:** `POST /auth/register` и `POST /auth/login` отвечают 404.
*   [x] **Управление токенами:**
    *   Успешная ротация токенов с использованием валидного refresh токена (старый токен становится `revoked`).
    *   Отказ в обновлении токена, если использован отозванный (`revoked`) refresh токен (ожидается 401).
    *   Отказ в обновлении токена, если использован истекший refresh токен (ожидается 401).
    *   Отказ, если вместо refresh токена передан access токен.
    *   Ротация и logout записывают `revoked_at`; ротация связывает токен с преемником (`replaced_by_id`).
    *   Повтор в пределах 30 секунд после ротации (ответ не дошёл) выдаёт новую пару и отзывает недошедшую: у цепочки одна активная сессия, `sid` новой пары указывает на её refresh-токен, другие сессии не затронуты. Повтор после ротации или logout новой пары и повтор токена без `replaced_by_id` (ротирован до миграции) — 401 без отзыва сессий. Через API: два `/refresh` с одним токеном — оба 200, работает только вторая пара.
    *   Давно отозванный (или отозванный logout без `revoked_at`) токен отзывает все активные сессии владельца, и отзыв переживает откат запроса.
    *   Токен с чужим `sub` не ротирует строку владельца (`401 INVALID_TOKEN`).
    *   Через API: после повторного предъявления украденного токена новая пара злоумышленника тоже отклоняется (`TestRefreshRotationAtomicity`).
*   [x] **Выход из системы (Logout):**
    *   Успешный выход с пометкой текущего access токена как `revoked`.
    *   Попытка использования `revoked` токена для доступа к защищенным эндпоинтам (например, `/me` возвращает 401).
    *   Попытка деактивации несуществующего токена и токена без `exp`.
    *   `jti` записывается в Redis с TTL не больше оставшегося срока жизни токена.
    *   Отзыв, записанный в Redis другим воркером, отклоняет токен (`TOKEN_REVOKED`) без локального состояния процесса.
    *   Сбой Redis при logout: `503 SERVICE_UNAVAILABLE`, токен остаётся действующим; `DELETE /me` — 503, аккаунт не удалён.
    *   Access-токен содержит `sid` — id строки своего refresh-токена в `tokens`.
    *   После logout refresh-токен той же сессии отклоняется (`401 TOKEN_REVOKED`), в том числе после ротации; refresh-токен другого устройства продолжает работать.
    *   Сбой Redis при logout откатывает и отзыв refresh-токена: `/refresh` после 503 проходит.
*   [x] **OAuth Авторизация:**
    *   Успешный вход или регистрация через Google (проверка валидации id_token и создания пользователя).
    *   Успешный вход или регистрация через Apple (проверка валидации identity_token и создания пользователя).
    *   Сохранение URL аватара при первом входе через Google.
    *   Автоматическое обновление `avatar_url` и `name` существующего пользователя при повторном входе через Google.
    *   Fallback-поля `avatar_url` и `name` в запросе `POST /api/v1/auth/google`, если в Google ID-токене отсутствует клейм `picture` из-за локального кеша.
    *   Возврат DTO профиля `user` (`UserResponse`) в `TokenResponse` при успешной авторизации.
    *   Проверка ID-токенов на реальной RSA-подписи (`test_oauth_verification.py`): токен для любого из нескольких client ID принимается; отклоняются (401 `INVALID_CREDENTIALS`) чужой `aud`, неверный или отсутствующий `iss`, `email_verified=false` или отсутствует (Google), отсутствие `aud`/`exp`, просроченный токен, чужая подпись, пустой список client ID.
    *   Клиент JWKS Google/Apple создаётся один раз на воркер и переиспользуется между запросами (новый `AuthService` на запрос не сбрасывает кэш ключей).
*   [x] **Профиль пользователя и базовая валюта (`PATCH /api/v1/auth/me`):**
    *   Успешное получение базовой валюты по умолчанию (`USD`) в `GET /auth/me`.
    *   Успешное обновление имени, URL аватара и базовой валюты (`base_currency` -> `USD`, `EUR`).
    *   Имя сохраняется без пробелов по краям; пустое имя или из одних пробелов — 422, прежнее имя не меняется.
    *   Валидация допустимых кодов валют через централизованный перечень `CurrencyCode` (отклонение неподдерживаемой валюты со статусом 422).
    *   Защита эндпоинта от неавторизованного доступа (401 / 403).
    *   Автоматический подхват базовой валюты пользователя в AI-инсайтах (`/api/v1/insights/`), если параметр `currency` не передан клиентом.
    *   Автоматический пересчет финансов: атомарный пересчет `exchange_rate` и `base_amount` всех транзакций пользователя, инвалидация ETag бюджетов и кэша AI-инсайтов при смене `base_currency`; лимиты бюджетов остаются в своей валюте.
    *   Точность пересчёта: кросс-курсы (EUR -> USD = 1/0.92) не округляются до масштаба суммы (`TestBaseCurrencyRecalculationPrecision`; ошибка проявлялась только на Postgres).

*   [x] **Принятие юридических документов (LEG-01, `test_legal_consent.py`):**

    *   Удаление аккаунта оставляет согласия с `user_id = NULL` и `account_deleted_at`; очистка удаляет только записи старше `CONSENT_RETENTION_DAYS`. Ротация ключей PII пересчитывает индекс в согласиях живых аккаунтов (`test_pii.py`).

### 2. Транзакции (Transaction Service)
*   [x] **Создание:** Успешное добавление транзакции (доход или расход).
*   [x] **Чтение:** Получение списка транзакций пользователя с фильтрацией (по датам, категориям и типу).
*   [x] **Обновление:** Изменение суммы, категории или даты существующей транзакции.
*   [x] **Удаление:** Удаление транзакции.
*   [x] **Изоляция данных:** Пользователь не может получить, изменить или удалить транзакцию другого пользователя.
*   [x] **Валидация:** Проверка на отрицательные суммы или некорректные типы операций.
*   [x] **Категории доходов:** Поддержка расширенных категорий (`freelance`, `investments`, `transfers`, `cashback`, `sales`). Валидация несовместимых категорий (отклонение `food` для дохода, отклонение `salary` для расхода с кодом 422).
*   [x] **Регулярные платежи (USAB-04, `test_recurring_payments.py`):** схема — валюта в верхнем регистре, пропущенные месяцы без повторов по возрастанию, длинное название обрезается, регулярный доход; отказ при несовместимой категории, дне 0/32, сумме 0, неподдерживаемой валюте, сроке раньше начала, месяце не в формате `YYYY-MM`, без `id`. `/sync`: создание и список по дню месяца, замена по id, удаление без затрагивания других, неверный платёж в `rejected` (`INVALID_CATEGORY` / `INVALID_SYNC_ITEM`) без падения батча, чужой id — `ID_CONFLICT` без перезаписи и удаления, старый клиент получает пустой `synced_recurring_payments`. `GET /recurring-payments`: 401/403 без токена, ETag и 304, правка и удаление меняют ETag; удаление аккаунта удаляет платежи. Общий помощник ETag (`not_modified_response`): совпавший, слабый, один из нескольких, «*» — 304; другой или без заголовка — нет.
*   [x] **Категории расходов (USAB-03):** `housing`, `communication`, `education`, `family`, `car`, `gifts`, `travel`, `beauty` принимаются в `/sync` для операций и лимитов; у каждой категории есть название на 4 языках для AI-отчёта.
*   [x] **Глобальный ETag и курсорная пагинация (`GET /transactions`):** ETag вычисляется по всей коллекции пользователя без привязки к `limit`/`cursor`. Заголовок `ETag` отдается только на первой странице выборки; страницы пагинации (`cursor != null`) не возвращают 304 и ETag. Запрос первой страницы с валидным `If-None-Match` возвращает 304 с заголовком `ETag`. Правка суммы или категории через `/sync` и пересчёт при смене базовой валюты меняют ETag (клиент со старым ETag получает 200); повтор записи без изменений ETag не меняет (только Postgres) — `TestTransactionsEtagOnEdits`.

### 3. Бюджеты (Budget Service)
*   [x] **Создание:** Установка лимита бюджета на определенную категорию и месяц/год.
*   [x] **Валидация категорий бюджета:** Бюджеты разрешены только для категорий расходов (`EXPENSE_CATEGORIES`); попытка установить бюджет на доходы отклоняется с кодом 422.
*   [x] **Мультивалютный подсчет spent и remaining:** Конвертация транзакций в разных валютах в `user.base_currency` по курсу транзакции или актуальному суточному курсу.
*   [x] **Валюта лимита и инвалидация ETag:** Лимит хранится в своей валюте (`currency`, по умолчанию базовая); при смене `base_currency` в `PATCH /api/v1/auth/me` сумма и валюта лимита не меняются, а `ETag` инвалидируется (клиент с сохраненным ETag получает 200 OK вместо 304).
*   [x] **Траты в валюте лимита:** Лимит в USD при базовой EUR считает траты в USD (чек в USD — по сумме, EUR — по кросс-курсу); лимит в базовой валюте считается по `base_amount` без запроса курсов; неподдерживаемая валюта — 422; upsert меняет валюту; синхронизация сохраняет `currency`, а элемент без неё (старый клиент) валюту не сбрасывает.
*   [x] **Проверка лимитов:** Расчет процента использования бюджета (превышение лимитов) на основе транзакций в этой категории.
*   [x] **Управление:** Обновление и удаление бюджетов, изоляция бюджетов между пользователями.

### 4. Синхронизация и Интеграции (Sync Service)
*   [x] Проверка логики обмена и синхронизации данных (состояние до и после синхронизации).
*   [x] **Идемпотентный UPSERT бюджетов:** Корректное сохранение и обновление бюджетов по ID или составному ключу `(category, month, year)` без дубликатов и без падения по уникальным констрейнтам.
*   [x] **Дедупликация пакетов:** Обработка повторяющихся элементов в пакете синхронизации и исключение дубликатов в ответе `synced_budgets`.
*   [x] **Лимит объема пакета:** Пакеты, содержащие более 500 элементов в списках транзакций, бюджетов или удалений, валидируются и отклоняются со статусом 422 (`max_length=500`).
*   [x] **Изоляция конфликтующих/чужих ID (TASK-12):** При передаче ID транзакции или бюджета, уже занятого другим пользователем, запись безопасно отклоняется в поле `rejected` с кодом `ID_CONFLICT`, предотвращая падение всего батча со статусом 500.
*   [x] **Объединенное удаление (N+1 оптимизация):** Удаление бюджетов из всех источников пакета (`deleted_budget_ids`, `deleted_budgets`, `check_deleted`) выполняется единым агрегированным SQL-запросом.
*   [x] **Устранение N+1 при коммите:** Сохранение объектов с `expire_on_commit=False` исключает отдельный цикл `refresh()` по каждой записи.
*   [x] **Границы входных данных синхронизации:** Описание длиннее 255 символов обрезается; суммы и лимиты больше `10^12` — запись в `rejected` с кодом `INVALID_AMOUNT` (`/sync`) или 422 (`POST`); переполнение суммы в базовой валюте — запись в `rejected` с кодом `INVALID_TRANSACTION_AMOUNT` (`/sync`), валюта без курса — `rejected` с кодом `INVALID_CURRENCY` или 400 `INVALID_TRANSACTION_AMOUNT` (`POST /transactions`); повтор батча с тем же клиентским `id` не создаёт дубль (`TestSyncInputLimits`, `TestTransactionInputLimits`).
*   [x] **Невалидная запись не роняет батч (SYNC-03):** неизвестная или неподходящая категория, неподдерживаемая валюта, сумма вне диапазона, некорректные дата, тип или `id` — запись в `rejected` с кодом `INVALID_CATEGORY` / `INVALID_CURRENCY` / `INVALID_AMOUNT` / `INVALID_SYNC_ITEM`, остальные записи сохраняются; клиент не может подставить своё `invalid_items`, в схеме запроса его нет — это приватный атрибут модели (`TestSyncInputLimits`). Предупреждение pydantic `UnsupportedFieldAttributeWarning` в тестах — ошибка (`pytest.ini`).
*   [x] **SyncService без HTTP-слоя:** возвращает `SyncResponse` и фиксирует данные; повтор ID в батче сохраняется один раз; ошибка БД откатывает весь батч и даёт `SYNC_FAILED` 500 (`tests/test_sync_service.py`).
*   [x] **Корректная обработка исключений (TASK-13):** Непредвиденные системные сбои возвращают 500 `SYNC_FAILED` (вместо маскировки под 400), а доменные `AppException` пробрасываются с исходными кодами и деталями.
*   [x] **Изменения с прошлой синхронизации (`GET /sync/changes`):** без `since` — все транзакции по `(updated_at, id)`; с `since` — только изменённые позже (с запасом в минуту); удаления через `DELETE /transactions/{id}` и через `/sync` попадают в `deleted_transaction_ids`, несуществующие и чужие ID — нет; повторное создание с тем же id снимает отметку удаления; курсор проходит все изменения без повторов, удалённые — только на первой странице; чужие изменения не видны; повреждённый курсор — 400 `INVALID_CURSOR`, `limit` вне 1..500 — 422; журнал удаляется вместе с пользователем (`tests/test_sync_changes.py`).

*   [ ] **Проверка Rate Limiter в боевых условиях:** Провести нагрузочное тестирование с реальных IP адресов или через балансировщик, чтобы убедиться, что `X-Forwarded-For` или реальные IP корректно определяются.
*   [ ] **Дашборд Load Testing:** после деплоя (и `docker compose restart prometheus`) в Prometheus → Status → Targets цели `node`, `postgres`, `redis` в состоянии UP; на дашборде все панели показывают данные (панели 5xx и ошибок в логах пустые при отсутствии ошибок), во время smoke-прогона растут RPS и соединения Postgres.
*   [ ] **Нагрузочное тестирование прода:** по [loadtest/README.md](loadtest/README.md) — smoke, ступени до 50 RPS, soak 40 минут, spike и double spike, холодный старт после перезапуска API, массовая оффлайн-синхронизация, стресс до отказа; критерии успеха из той же инструкции, после прогона `cleanup` и 0 тестовых пользователей в БД.
*   [ ] **Concurrent requests (Состояние гонки):** При быстром клике "создать транзакцию" в UI убедиться, что транзакция не дублируется.
*   [ ] **Синхронизация на плохой сети:** Имитация потери пакетов (throttle network в DevTools браузера/телефона) при вызове `/sync` или долгих запросах, чтобы убедиться, что приложение не зависает и корректно показывает ошибку таймаута.
*   [ ] **UI/UX: Истечение сессии:** Оставить вкладку открытой до истечения срока действия refresh токена. Убедиться, что при возобновлении активности приложение плавно переводит пользователя на экран логина без показа "сырых" 401 ошибок.
*   [ ] **Сетевой периметр на проде:** снаружи `nmap <IP>` показывает только 22/80/443; `curl -m 5 http://<IP>:8000` — нет ответа; `curl -I http://<IP>` — соединение закрыто (444); `curl -I https://api.getbalanceai.app/metrics` — `403`; `curl -I https://api.getbalanceai.app/docs` — `401`, с `-u <логин>:<пароль>` — `200`; `https://api.getbalanceai.app/api/v1/...` работает с Bearer-токеном без basic auth.
*   [ ] **Grafana за basic auth:** `https://grafana.getbalanceai.app` показывает окно basic auth, затем форму входа Grafana; Viewer видит дашборды, пункт Explore недоступен (`/explore` перенаправляет на главную).
*   [ ] **Дашборды Grafana без Angular:** после обновления Grafana все пять дашбордов (FastAPI Observability, Docker monitoring, Cadvisor exporter, Loki Logs Dashboard, Load Testing) открываются без баннера об устаревших Angular-панелях, графики и таблицы показывают данные; пользователи и роли из прежнего тома `grafana_data` сохранились.
*   [ ] **Принятие условий в приложении (LEG-01):** вход с отметкой на телефоне — в `user_consents` две записи с языком, платформой и версией приложения; у аккаунта, созданного до LEG-01, — экран новой версии, после «Принять» данные синхронизируются.
*   [ ] **Одобрение и реальный вход через OAuth:** Протестировать вход с реальными Google и Apple аккаунтами из мобильного приложения. Убедиться, что внешние токены успешно обрабатываются сервером.
