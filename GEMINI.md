# Инструкции и регламент разработки для агентов (GEMINI.md)

Данный документ определяет стандарты качества, правила рабочего процесса и инженерную культуру при разработке проекта **Finance App API (getbalanceai_api)**.

Каждый агент обязан следовать этим инструкциям при выполнении любой задачи.

---

## 1. Базовые принципы и культура кода

* **Production-grade качество**: Это боевое финансовое приложение. Код должен быть надежным, безопасным, производительным, типизированным и поддерживаемым.
* **Никакого мусора и ИИ-пометок**:
  * Категорически запрещены комментарии вида `# AI generated`, `# Generated by Gemini`, `# Temporary fix`, `# TODO for AI`, отладочные метки или мусорные заметки.
  * Все комментарии и docstrings должны быть профессиональными, лаконичными и описывать предметную область на русском языке.
  * Не оставлять закомментированный неиспользуемый код, отладочные `print()` или временные файлы.
* **Архитектурный источник правды**: Вся разработка опирается на [ARCHITECTURE.md](file:///c:/Projects/getbalanceai_api/ARCHITECTURE.md) и [RESPONSE_FORMAT.md](file:///c:/Projects/getbalanceai_api/RESPONSE_FORMAT.md). Запрещено нарушать границы слоев.

---

## 2. Жизненный цикл задачи (Workflow)

При получении любой задачи агент строго следует следующему регламенту:

### Шаг 1. Ветвление в Git
* **Всегда ответвляться от актуального `main`**:
  ```bash
  git checkout main
  git pull origin main
  git checkout -b <type>/<task-semantic-name>
  ```
* Использовать семантические префиксы:
  * `feat/` — новый функционал
  * `fix/` — исправление багов
  * `refactor/` — рефакторинг без изменения контрактов
  * `test/` — добавление или правка тестов
  * `docs/` — обновление документации
  * `chore/` — инфраструктурные и сборочные изменения
* **Прямые коммиты в `main` строго запрещены** (заблокированы pre-commit хуком).

### Шаг 2. Разработка с учетом слоев (Layered Architecture)
* Соблюдать строгую изоляцию ответственности:
  * **Routers** (`app/routers/`): только HTTP, валидация параметров, DI, возврат `ApiResponse[T]`.
  * **Schemas** (`app/schemas/`): DTO валидации Pydantic v2.
  * **Services** (`app/services/`): чистая бизнес-логика, транзакции, интеграции, предметные ошибки.
  * **Models** (`app/models/`): SQLAlchemy 2.0 декларативные модели (`Mapped`).
  * **Database** (`app/database.py`): управление сессиями и транзакциями через `UnitOfWork` / `get_db`.
* При работе в конкретных директориях автоматически применяются локальные правила:
  * [app/routers/GEMINI.md](file:///c:/Projects/getbalanceai_api/app/routers/GEMINI.md)
  * [app/services/GEMINI.md](file:///c:/Projects/getbalanceai_api/app/services/GEMINI.md)
  * [app/models/GEMINI.md](file:///c:/Projects/getbalanceai_api/app/models/GEMINI.md)
  * [tests/GEMINI.md](file:///c:/Projects/getbalanceai_api/tests/GEMINI.md)
  * [migrations/GEMINI.md](file:///c:/Projects/getbalanceai_api/migrations/GEMINI.md)

### Шаг 3. Тестирование
* При добавлении или изменении логики агент **обязан** обновить или расширить юнит- и интеграционные тесты в `tests/`.
* Покрывать как успешные кейсы, так и негативные сценарии (ошибки валидации, 401/403/404, лимиты).
* **Не запускать тесты автоматически при коммите/пуше**: перед коммитом и пушем агент **не должен** сам прогонять тесты. Пользователь прогоняет тесты самостоятельно либо они выполняются хуками. Если требуется прогон — явно уведомить пользователя и предоставить команду:
  ```bash
  pytest tests/ -v
  ```

### Шаг 4. Линтеры и форматирование кода
* Код должен строго соответствовать стандартам:
  * **flake8** с конфигурацией из `.flake8` (максимальная длина строки — 125, исключения E203, W503).
  * **black** (`--line-length=125`).
  * **isort** (`--profile=black`).
* Не оставлять неиспользуемых импортов, синтаксических предупреждений или некорректных отступов.
* **Не запускать линтеры перед пушем/коммитом**: на это настроены pre-commit хуки репозитория и пользователь сам выполняет эти проверки. Агент пишет код чисто сразу, без необходимости вызова проверочных команд перед пушем.

### Шаг 5. Миграции базы данных
* Если задача затрагивает схему БД (`app/models/`):
  1. Создать миграцию Alembic и проверить сгенерированный `upgrade()` и `downgrade()`.
  2. **Обязательно предупредить пользователя и дать готовую команду**:
     ```bash
     alembic upgrade head
     ```

### Шаг 6. Контейнеризация и окружение
* Если изменены `requirements.txt`, `.env`, `.env.example`, `Dockerfile` или `docker-compose.yml`:
  * Явно уведомить пользователя о необходимости пересборки/перезапуска сервисов и предоставить команду:
    ```bash
    docker compose down
    docker compose up --build
    ```

### Шаг 7. Обязательный этап Код-Ревью (Senior Reviewer)
Перед сдачей результата пользователю проводится критическое код-ревью в роли независимого Senior Reviewer по чек-листу:
1. **Чистота кода**: нет ли мусорных комментариев, отладочных принтов, временных костылей, лишних файлов.
2. **Архитектура**: соблюдены ли границы слоев, контракты [RESPONSE_FORMAT.md](file:///c:/Projects/getbalanceai_api/RESPONSE_FORMAT.md) и `ApiResponse[T]`.
3. **Безопасность**: проверяются ли права текущего пользователя (`current_user.id`), нет ли утечек данных, безопасны ли SQL-запросы.
4. **Производительность**: нет ли проблем N+1, избыточных обращений к БД, блокировок, утечек ресурсов или сессий.
5. **Расширяемость**: понятен ли код, декомпозирован ли он, можно ли его легко протестировать и масштабировать.

  * [README.md](file:///c:/Projects/getbalanceai_api/README.md) — при изменении шагов запуска, переменных окружения или команд.

  * [TEST_CHECKLIST.md](file:///c:/Projects/getbalanceai_api/TEST_CHECKLIST.md) — при добавлении новых сценариев тестирования.

### Шаг 9. Чистота Git
* Убедиться через `git status`, что в репозиторий не попали временные файлы, дампы, локальные базы SQLite, кэши (`__pycache__`, `.pytest_cache`) или незафиксированные артефакты.
